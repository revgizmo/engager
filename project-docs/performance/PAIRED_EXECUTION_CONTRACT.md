# Paired same-worker A/A execution, version 1.0.0

This repository-only contract implements the next controlled-calibration step
for [#471](https://github.com/revgizmo/engager/issues/471). One manual Linux job
executes the same pinned package and harness twice: **reference, then repeat**.
Each block invokes the complete existing six-scenario measurement controller,
with five fresh R observation processes per scenario: 30 observations per block,
60 per complete pair. The two blocks are separate controller invocations.

This implementation has not been demonstrated with a real hosted paired run.
Its bounded local tests use fabricated values and actual child-process launches;
those values are validator fixtures, never benchmark measurements. A later pilot,
hosted artifact inspection, baseline admission, threshold selection and enforcement
require their separately scoped decisions. Human product QA remains separate.

## Files and invocation provenance

`scripts/benchmarks/paired_execution.R` preserves the existing measurement
schema 2.0.0. A complete output directory contains `reference.json`, `repeat.json`
and `pair.json`. The pair manifest has exactly `paired_schema_version: "1.0.0"`,
`status: "complete"` and an ordered array of two block receipts. Each receipt has:

| Field | Contract |
| --- | --- |
| `receipt_schema_version` | Exactly `1.0.0` |
| `pair_id` | 32 random bytes, lowercase hex, generated by the parent |
| `invocation_id` | 32 random bytes, lowercase hex, generated inside that child before measuring; distinct from parent and other child |
| `block`, `position` | `reference`,1 then `repeat`,2 |
| `context` | Constrained repository, actual GitHub run ID/attempt, fixed `paired_benchmarks` job key, fixed `paired-benchmarks.yaml` workflow and workflow commit |
| `source` | Package checkout commit/tree and extended source manifest |
| `started_at_unix_ms`, `finished_at_unix_ms` | UTC epoch milliseconds around the measurement controller; finite exact integers below 2^53, ordered, at most 120-minutes apart |
| `previous_measurement_sha256` | Null for reference; reference's raw measurement SHA-256 for repeat |
| `measurement_sha256` | SHA-256 of that child's exact raw measurement 2 bytes |

Both children inherit the actual workflow/run/attempt/job environment. Production
requires `GITHUB_ACTIONS=true`, `workflow_dispatch`, a clean committed checkout,
and HEAD equal to both `GITHUB_SHA` and `GITHUB_WORKFLOW_SHA`. The workflow-ref
environment must identify this repository and the paired workflow; arbitrary ref
text is not retained. `GITHUB_JOB` records the fixed job key, not an invented
numeric GitHub job ID. The non-matrix, single-job workflow plus run ID and attempt
identify the job within the producer contract. Later hosted review must reconcile
these fields with actual run/job metadata.

Each child checks source/context before and after measuring. Its receipt is
written only after `measurement_run()` succeeds and its newly created raw output
passes strict validation. There is no production command to wrap an existing
measurement file. The parent starts reference, checks its receipt against the
fresh parent identity/source/context, then starts repeat with the reference hash.
It checks both children against its own unchanged snapshots. Reference completion
must precede or equal repeat start; the measurement 2 whole-second timestamp must
fall within its child's window at whole-second precision. The report records
the gap between blocks in seconds. Wall-clock timestamps are snapshot evidence;
they do not prove monotonic clocks or equivalent host conditions.

The extended manifest covers the existing measurement controller, runtime helper,
ordinary workflow and workloads, plus the paired producer, comparison helper and
actual paired workflow. Its fixed-order IDs and raw SHA-256 hashes are hashed as:

```text
engager-paired-sources-v1\n
controller:SHA256\n
runtime:SHA256\n
workflow:SHA256\n
workloads:SHA256\n
paired_producer:SHA256\n
comparator:SHA256\n
paired_workflow:SHA256\n
```

The algorithm label is `sha256-paired-sources-v1`. The first four file entries
must exactly match each measurement's existing runtime harness manifest. Extended
source manifests, commit/tree and context must match across blocks. Source bytes
must match the producer's startup snapshots throughout production. This extends
the existing snapshot limitation: R begins interpreting the producer before its
startup snapshot; no continuous source or process attestation is claimed.

Receipts are invocation provenance from this reviewed producer, **not cryptographic
proof of trustworthy execution or GitHub authenticity**. A party able to rewrite
the whole evidence bundle and its expected hashes can fabricate receipts and
metadata. Consumers must independently verify the expected manifest checksum and
its commit/tree/source hashes against the reviewed source and hosted run evidence.
The comparison helper checks structure and internal bindings; it does not contact
GitHub, attest installed package binaries or maintain a global replay registry.
Do not count a copied pair twice as an independent job. No paths, host names,
serial numbers, transcript text or participant data are retained in these receipts.

## Strict comparison and compatibility

```sh
Rscript scripts/benchmarks/paired_execution.R compare PAIR_JSON PAIR_SHA256 OUTPUT_JSON
```

Supply an independently checked lowercase SHA-256 for `pair.json`. The helper
reads the two fixed sibling filenames, verifying each raw checksum and parsing
the same bytes that were hashed. It rejects missing/extra/duplicate JSON keys,
named arrays, incomplete/duplicated/reused receipts, equal measurement hashes,
wrong parent/job/run/attempt/source association, relabeled old measurement files,
invalid order/windows, partial blocks and inexact summary arithmetic. Receipt
hashes bind the raw measurement files; changing a block label cannot turn an
ordinary measurement file into a pair manifest.

Only a fully validated explicit pair receives the same-job exception. The
ordinary `compare_measurements.R` stays unchanged: ordinary measurement 1/2
artifacts from the same run/attempt still produce `same_run_identity`. Valid
legacy 1 measurements remain readable there and non-comparable because their
runtime evidence is absent. Paired receipts require measurement 2; no old artifact
is assigned retrospective execution identity.

Every other ordinary comparator rule remains: all observation assertions, budgets,
workloads, schemas and runtime snapshots validate; equal-but-unknown runtime facts
remain non-comparable, as do dependency/image/hardware or other runtime mismatches.
Source/context/order failures are invalid input and publish no comparison report.
Runtime incompatibility produces a retained `non_comparable` report without numeric
scenario differences. Complete means two valid executions, not compatible runtime
facts or a performance pass.

The report retains comparison schema 2 and adds
`paired_comparison_schema_version: "1.0.0"`, the pair-manifest checksum, complete
execution receipts and `separation_seconds`. Baseline/candidate fields mean
reference/repeat. Comparable pairs report six scenarios' median/min/max elapsed
seconds and absolute GNU-time peak RSS KiB, signed/absolute differences and ratios.
Exact recomputed arithmetic and zero/overflow ratio statuses are preserved.
Every report is descriptive with `regression_verdict: "not_assessed"` and
`trusted_baseline: false`; no regression limit or accepted baseline is introduced.

Exit codes:0 for a completed producer or descriptive comparison;2 for invalid
input/execution;3 for a retained non-comparable report;4 for a blocked comparison
output. Errors use bounded messages. The producer reserves a new directory once,
refuses even existing empty directories/dangling links, and publishes the pair
manifest last. Each final file uses atomic no-replacement hard-link publication
on the same filesystem. A publication interruption may leave individual files;
without a valid manifest and both hash-matching blocks these are not a complete
pair. A failed/interrupted child publishes no pair into the destination. Output
locations must be outside the committed checkout so source cleanliness remains
meaningful. Existing outputs must never be reused as retry destinations.

## Manual workflow and time budget

`.github/workflows/paired-benchmarks.yaml` has only `workflow_dispatch`, one
`ubuntu-latest` job and no matrix/retries. It checks out the dispatched commit,
installs its package/dependencies once, and invokes the parent producer. Each
child has a 7200-second process timeout. The 300-minute job ceiling covers two
120-minute blocks plus at most 60 minutes for setup/comparison/upload; slow setup
can reduce the remaining execution time and fail the job, never justify a retry.
This is below GitHub's documented 360-minute hosted-job maximum, checked 2026-09-14.
See [GitHub Actions limits](https://docs.github.com/en/actions/reference/limits).

The workflow uploads only the two raw measurements, completed manifest and
comparison report after successful production/validation. A non-comparable report
is retained as a disposition, not converted into numeric results or a performance
pass. Setup failures, child timeouts and absent/partial artifacts remain failed
attempts in hosted run records; a future study must account for every attempt,
including those with no uploaded artifact. Do not infer a success-only study from
the uploaded directories. No dispatch or generated hosted artifact download is
part of implementing this workflow.

Normal CI runs only the bounded new contract tests alongside existing benchmark
contract tests. The existing single-block Benchmarks triggers/budgets are unchanged;
no push or pull request can automatically launch the paired workflow. Test-only
dependency injection uses R function arguments with fabricated values; there is
no CLI or environment bypass that makes production accept local runtime evidence.

## Interpretation and next decision

Fixed reference-then-repeat order, shared filesystem/package caches and host
activity can favor the second block. The workflow does not flush caches, upgrade
between blocks, retry, randomize or assert cold starts. Matching snapshots cannot
establish continuous runtime equivalence, transitive/native dependency or installed
build identity, isolation from host contention, or a causal performance effect.

Each scenario yields one paired contrast per job. Its five within-block
observations are not five independent host environments. Preserve every attempt
and runtime group; do not pool levels across different hardware/image/dependency
groups or select only favorable pairs. A future bounded pilot can assess whether
the method yields complete comparable pairs and recurring order effects. It cannot
by itself establish confidence intervals, tail behavior, false-positive rates,
regression thresholds or tactical performance improvements.
